## Результат (достаточно)

1. **События «Действия»** — изменение статьи сайта, дошедшее до серверной `main` (не «успешная выкладка»). Источник
   один для владельца и сотрудника: первая линия `main` на сервере (`ls-remote` → `fetch --no-write-fetch-head`
   названного SHA; след `origin/main`, `FETCH_HEAD`, `gitPush.mjs` и замок публикации не трогаются, публикация не
   меняется). Запись: вид (добавление/правка/переименование/удаление), статья, локаль, прежний и новый путь/адрес,
   дата коммита, когда программа увидела, автор, коммит, точная дельта (текст разницы против первого родителя и
   счёт строк); описание пустое. Слияние — один раз против первого родителя; переименование — одна запись; статья —
   `файлСтатьи` в корнях `наСайте`, картинки и `_category_.json` — нет. Ключ (коммит, путь): повтор без дублей.
2. **Ручное SEO-событие** — отдельный тип (дата, текст, необязательный адрес); в операции 1 — хранение и ручка.
3. **Search Console** (`https://learn.bimcore.one/`, настройкой): дневные показы, переходы, CTR, позиция по
   `page` × `date`, тем же ключом (`webmasters.readonly`), не чаще `обновлениеЧасов`; неполные дни помечены. После
   полного ответа запрошенные дни заменяются целиком одной транзакцией; обрыв ничего не меняет.
4. **Хранилище:** SQLite (`node:sqlite`, лениво; нет поддержки — нет функции) в `<материалы>/editor/.analytics/` со
   своим `.gitignore`; WAL, `busy_timeout`, короткие `BEGIN IMMEDIATE` с откатом, сеть вне транзакций; одна
   дверь-модуль, заменимая серверной базой.
5. **Приватность:** нет ключа — нет функции, без надписей об ошибке (у сотрудника). Ключ проверяется до открытия базы;
   адрес API и область постоянные, без перенаправлений; наружу — свои коды; секрет не в Git, окне, журналах, базе.
6. **Описание пишет только ИИ** (слово владельца 24.09). Ручка записи описания к событию по (коммит, путь): сперва
   подтягивает свежие события. Правило «ИИ, опубликовав статью, сразу заполняет описание» ведущий вносит в
   `playbook-publish` базы после приёмки.
