## Правило проверки по риску

Класс выбирается по худшему возможному последствию, а не по числу строк или имени файла.

| Класс | Что меняется | Обязательный путь |
|---|---|---|
| **1. Видимое и обратимое** | надпись, стиль, расположение, чистая кнопка поверх уже проверенного действия | ближайшая проверка логики, если она менялась; типы для TS/TSX; один проход изменённого экрана самим исполнителем; Codex, полный набор, корпус и сборка запрещены |
| **2. Данные статьи** | сохранение, чтение, история, изображения, локали, MDX, frontmatter, путь статьи | контролёр до кода; адресные тесты успеха и отказа; типы; полный набор один раз после последней правки; корпус только при изменении чтения или записи; сборка только при изменении выдаваемого MDX, пути или языковой структуры; проба на копии статьи; контролёр после кода |
| **3. Публикация и необратимость** | состав публикации, Git, push, архив, удаление, перенос живых данных | всё из класса 2 по затронутому риску; настоящий временный Git с успехом, отказом и повтором; полная сборка того же снимка; точный состав коммита; сухой маршрут; контролёр после кода; отдельное подтверждение владельца перед настоящей отправкой |

Изменение интерфейса получает более высокий класс, если через него меняется опасное действие. Изменение
локали, влияющее на состав публикации, относится к классу 3. Полный набор тестов не перезапускается
после каждой мелкой починки: сначала адресный тест замечания, затем обязательный итоговый набор один раз.

## Несократимые свойства

1. Ошибка не теряет текст и не показывает ложное «Сохранено».
2. Открытие и сохранение без правок не меняют файл.
3. Действие затрагивает только выбранную статью, локаль и явно показанные файлы.
4. Проверки, сборка, коммит и отправка относятся к одному снимку текста, настроек и опубликованной ветки.
5. Коммит совпадает с показанным составом, включая добавления, удаления и переименования.
6. Push идёт только в ожидаемые ветку и адрес после подтверждения владельца.
7. Удаление опубликованного означает восстанавливаемый архив, а не безвозвратное стирание.

## Рабочая ветка и контрольные коммиты

`main` хранит только результаты, принятые владельцем живой пробой и верхнеуровневым Codex. Каждая
новая функциональная операция редактора начинается от чистого `main` в отдельной локальной ветке:
`feature/editor-<суть>` для новой возможности или `fix/editor-<суть>` для дефекта. В
`CURRENT_TASK.md` записываются базовый коммит и точное имя рабочей ветки.

В рабочей ветке Claude делает локальные контрольные коммиты после законченной смысловой части, перед
остановкой сессии и прежде чем операция переживёт перезапуск компьютера. Для такого коммита не нужно
отдельное согласие владельца; сообщение называет фактическую суть, а push рабочей ветки запрещён без
прямого слова владельца. Пути каждого коммита добавляются поимённо; `git add .` запрещён. Перед
переключением ветки незакоммиченных изменений быть не должно, сервер редактора останавливается и
после переключения запускается заново.

Если результат отклонён, Claude возвращается на `main`, доказывает, что он не изменился, и удаляет
локальную рабочую ветку только после сохранения либо явного отказа от всех её незакоммиченных файлов.
Если результат принят, проверки, живая проба и допуск относятся к точному `HEAD` рабочей ветки. При
неизменившемся `main` он получает этот результат через `git merge --ff-only`. Если `main` за время
работы сдвинулся, сначала он вливается в рабочую ветку, после чего затронутые проверки и живая проба
повторяются; только затем `main` переводится вперёд. После сверки `main` рабочая ветка удаляется.

Настоящая публикация статей выполняется только из `main`. Если она срочно нужна во время длинной
операции редактора, Claude сначала делает контрольный коммит, переключается на `main`, а после
публикации возвращается в рабочую ветку и синхронизирует её по правилу выше.

## Как выполняется одна операция

1. Владелец и верхнеуровневый Codex формулируют один видимый результат. `CURRENT_TASK.md` хранит
   только этот контракт и не превышает 60 строк.
2. Claude сверяет контракт с `BUSINESS.md` и `SPEC.md`, выбирает класс, проверяет базовый коммит и
   рабочую ветку по правилу выше и не начинает соседние работы.
3. Для классов 2 и 3 Claude до кода вызывает низкоуровневого контролёра по `codex-gate`. Контролёр
   проверяет класс, называет не более трёх затронутых свойств и требует убрать лишнюю работу.
4. Claude пишет код и выполняет только проверки своего класса. На одну рабочую папку приходится один
   пишущий помощник.
5. Находка вне операции не исправляется. Она записывается хвостом; работа останавливается только если
   находка доказывает потерю данных, неправильную публикацию или невозможность закончить результат.
6. Для классов 2 и 3 итоговый контролёр читает фактический diff и доказательства. После починки
   разрешён один повтор по замечанию и обязательный итоговый набор, но не новый широкий аудит.
7. Claude сам проходит сценарий, обновляет `handoff.md` и оставляет программу открытой. Отчёт владельцу
   не длиннее десяти строк и написан по `REPORT.md`.
8. До пробы владельца Claude фиксирует законченный результат контрольным коммитом и оставляет дерево
   чистым. Владелец свободным текстом сообщает верхнеуровневому Codex, что увидел. После этого новый
   функциональный коммит аннулирует пробу и требует повторить изменённый сценарий. Claude записывает
   в handoff базовый коммит, имя ветки, её точный `HEAD` и полный `git status --short`. Codex читает
   контракт, handoff, status и `git diff <base>..<head>`. Нет блокера — пишет
   `APPROVED_TO_MERGE branch=<name> head=<sha> base=<sha>`. Допуск действует только для этой тройки;
   новый коммит, движение `main` или грязное дерево его отменяют. Перенос в `main` выполняется без
   нового вопроса владельцу по правилу рабочей ветки выше.
9. Настоящую публикацию статьи, push живого контента, смену адреса и архивирование опубликованного
   подтверждает владелец непосредственно перед действием.

## Контролёр и границы замечаний

Каждый вызов контролёра независим: `codex exec --ephemeral --sandbox read-only`. Постоянной сессии,
`resume`, `reviewer.json`, ревизий handoff и второго итогового аудитора нет. Контролёр возвращает:

- `GO` — продолжать;
- `SHRINK` — убрать названную лишнюю работу;
- `BLOCK_REAL_RISK` — найден воспроизводимый путь к потере текста, чужому файлу, неверной локали,
  неправильному коммиту, публикации другого снимка или необратимому удалению.

Стиль, предпочтительная архитектура, будущая функция и искусственный ввод без реального ущерба не
блокируют. Одно замечание должно ссылаться на конкретное место, сценарий и нарушенное свойство.
Блокеров не больше трёх.

## Вопросы владельцу

Технических вопросов владельцу нет. Перед продуктовым вопросом Claude передаёт контролёру точный
вопрос и контекст. Контролёр обязан самостоятельно восстановить цель и выбрать:

- `RESOLVE_WITHOUT_OWNER` — решение следует из контракта или существует минимальный обратимый путь;
- `REFRAME_REQUIRED` — варианты Claude неполны либо операция разрослась; её нужно уменьшить;
- `OWNER_REQUIRED` — без владельца меняется обычное пользовательское поведение или возникает
  необратимый риск.

За операцию допускается максимум один собранный пакет продуктовых вопросов. При
`RESOLVE_WITHOUT_OWNER` и `REFRAME_REQUIRED` вопрос владельцу не показывается. Обязательное
подтверждение настоящей публикации или разрушительного действия этим фильтром не отменяется.

## Передача между чатами и сессиями

`CURRENT_TASK.md` передаёт намерение от владельца и верхнеуровневого Codex к Claude. Новая операция
заменяет карточку целиком; история остаётся в канонических документах.

Игнорируемый `editor/.coordination/handoff.md` передаёт результат обратно и не превышает 50 строк:

1. операция, класс, HEAD и статус;
2. результат Claude владельцу;
3. короткие доказательства;
4. наблюдения владельца;
5. ответ верхнеуровневого Codex и следующее действие.

Файл не хранит ID, ревизии и историю. Владелец не переносит технический текст. После перезапуска
новая сессия читает контракт, handoff и фактический Git и продолжает с названного следующего действия.
Если handoff отсутствует после нового checkout, Claude создаёт его до кода по этой структуре;
отсутствие файла не отменяет передачу и окончательную сверку.

### З0. Файл состояния — от файла версии, а не от папки

**Что сможет владелец.** Положить статью файлом внутрь раздела, не ломая страницу самого раздела.
**Правило имени, принятое здесь и обязательное.** Единственный формат статьи — `.mdx` (решение
владельца 2026-08-12, `DECISIONS.md`), поэтому правило задаётся только для него: `index.mdx` →
`_state.json` (как сегодня), `<имя>.mdx` → `_<имя>.state.json`. Случая `.md` не существует, и
столкновения имён из-за разных расширений тоже. Имя строится из настройки
`хранение.файлСостояния`, а не пишется в коде.
**Без миграции.** Существующие физические файлы состояния не переносятся, не переименовываются и
не создаются автоматически. Сегодня их на диске нет вовсе; появятся — правило меняет только то,
где программа ищет и пишет состояние впредь, а старые файлы остаются на своих местах.
**Входит.** Правило имени одним местом (`library.mjs`, `articleState.mjs`) и все его читатели и
писатели — реестр, сохранение, удаление, создание, подготовка; закрывается хвост В1-20. Здесь же
заводится команда корпусного прогона (её определение — в шаге 5) — она нужна воротам этого же задания.
**Не входит.** Признак «страница раздела» и категория статьи-файла (решено владельцем, делает З16) · соседи при удалении и полноценное архивирование статьи-файла (З13).
**Порядок внутри задания.** Сначала заводится команда корпусного прогона и запускается на текущем
коде: без этой отметки нечем доказать, что правка ничего не изменила. **Отметка обязана быть нулевой** —
ни одного изменившегося файла. Нашлись изменения ещё до правки — это чужой дефект, а не допустимая
точка отсчёта: задание останавливается, находка идёт владельцу отдельно (шаг 4). Сравнение «до было
пять изменений, после тоже пять — значит всё в порядке» правилом не считается. Только после нулевой
отметки меняется правило имени.

**Инварианты — верны для любых входов, а не только для примера приёмки.**
1. Путь файла состояния вычисляется из полного пути конкретного файла версии, а не из одной её папки.
2. Два разных файла версии (`.mdx`) не могут получить один путь состояния.
3. Правило пути живёт в одном месте; реестр, сохранение, создание, удаление и подготовка зовут его,
   а не считают сами.
4. **Миграции нет.** Задание не переименовывает, не перемещает, не создаёт и не удаляет ни одного
   существующего файла состояния. У статей, лежащих папкой с `index.mdx`, вычисленный путь до
   правки и после совпадает; у статьи, лежащей файлом, он становится своим — это и есть смысл
   задания, а не перенос данных.

**Матрица сценариев (проверяется вся).** Существующая статья папкой · статья-файл рядом с
`index.mdx` · статья без файла состояния вовсе · статья в песочнице · создание статьи-файла ·
одинаковые имена файлов в разных папках · имя с несколькими точками.

**Приёмка — обязательный минимум; сценарии из инвариантов исполнитель выводит сам.**
- Перечень физических файлов состояния до правки и после совпадает целиком; ни один файл не создан,
  не удалён и не переименован.
- Готовность каждой живой статьи до и после правки одна и та же.
- Пробная статья-файл в уроках сохранена — файл состояния страницы раздела не изменился ни байтом,
  её готовность прежняя; у пробной статьи своё состояние, и оно **не совпадает** с `_state.json`
  страницы раздела.
- Корпусный прогон зелёный, круг ворот без находок.

**Доказательства в инженерную запись.** Итог всех обязательных команд ворот · имена новых тестов · перечень путей
состояний до и после · запись живой проверки по шагу 6 · число проверенных файлов в корпусном прогоне.

### З1а. Закрытие ядра подготовки

**Что сможет владелец.** В окне пока ничего; ядро становится пригодным к подключению.
**ЗАКРЫТО 2026-08-13** по правилу закрытия блока в редакции того же дня: критерии приёмки ниже
выполнены, машинные проверки зелёные, живая проверка пройдена, кругов ворот пройдено двенадцать.
Оставшиеся замечания — неблокирующие хвосты в `PLAN.md`.
**Входит.** Круг ворот по правке адресов (хвост блока Б2 закрывается этим же кругом);
ключевые слова из блокера в просьбу по слову владельца (`BUSINESS.md` 7б.11): обязательные поля
категории (не рода — требования задаются по категории, решение совета 2026-08-10)
дают предупреждение у любой версии, `keywords: []` в файле остаётся блокером — от него падает сборка;
своя проверка «порядок в меню — число» (живой хвост, роняет сборку сайта); проверка длины описания.
**Не входит.** Сервер, окно, внешние этапы · просьба при открытии статьи (это окно, З1в).
**Приёмка.** Обязательный круг ворот пройден; статья без ключевых слов у видимой версии проходит
с предупреждением; `keywords: []` — блокер; «порядок в меню: два» — блокер с местом; документы
приведены к слову владельца в том же блоке.
**Инварианты.** Обязательное поле категории отсутствует — предупреждение у любой версии; поле
записано пустым списком — блокер у любой версии (от него падает сборка). Описание обязательно у
каждой версии без исключений. Проверка настройки идёт раньше проверок статьи: сломана настройка —
зелёного отчёта не бывает.
**Матрица сценариев.** Все поля заполнены · нет ключевых слов у видимой версии · нет у скрытой ·
`keywords: []` · «порядок в меню» словом · описание длиннее предела · настройка сломана.
**Доказательства в инженерную запись.** Итог всех обязательных команд ворот · имена тестов по каждому сценарию ·
перечень мест, где документы приведены к слову владельца.

> требования, инварианты и критерии приёмки остаются в силе как требования к маршруту публикации;
> фразы вида «кнопка неактивна без подготовки», «зовёт пройти подготовку заново», «статус готова к
> публикации ставит подготовка» описывают устройство, которого больше нет, и обязательными не
> являются. Порядок внутри публикации — `SPEC.md` 5.4 и `BUSINESS.md` Б11.

### З1б. Сервер подготовки

**Что сможет владелец.** Ничего видимого; появляется рабочая ручка.
**Входит.** Ручки старта и статуса; задача в памяти сервера, **ключ — сама статья, а не открытая версия**
(иначе две версии одной статьи готовились бы параллельно и обе ставили бы готовность всем), повторный запуск —
отказ, перезапуск сервера — честное «операции нет»; барьер: во время подготовки сохранение и
автосохранение по путям этой статьи отвечают отказом словами; снимок полного содержимого файлов
одним чтением; отпечатки файлов статьи и файлов состояния, сверка в конце; готовность ставится всем
существующим версиям только при совпавших отпечатках.
**Договор снимка.** Состав файлов берётся только из правила ядра «состав статьи». Будущий файл
комментариев (З9) расширяет одно это правило — тогда снимок, отпечатки, коммит и уборка получают его
сами, без переделки трёх заданий.
**Не входит.** Внешние этапы (З2) · окно (З1в).
**Состояния операции — договор, обязательный к соблюдению обеими сторонами.** `нет` (не запускалась
или сервер перезапущен) · `идёт` · `завершена` · `сбой`. Для каждого задано: какие команды
принимаются, что отвечает сервер, работает ли барьер сохранения, можно ли стартовать заново, когда
снимается барьер, сохраняется ли отчёт, ставится ли готовность. Состояние живёт в памяти сервера, ключом — статья. Требование к ключу задано результатом, а не
алгоритмом: **две языковые версии одной статьи обязаны давать один ключ, две разные статьи —
разные**. Строится он существующим правилом опознания статьи (`articleKey` в ядре) после приведения
разделителей пути к одному виду. Регистр символов не меняется: правила регистронезависимых путей в
проекте нет, и заводить его здесь нельзя.

| Состояние | Старт | Сохранение и автосохранение | Ответ на запрос хода | Готовность | Отчёт |
|---|---|---|---|---|---|
| `нет` | разрешён | разрешены | «операции нет» | не трогается | пуст |
| `идёт` | отказ «уже идёт» | отказ словами, текст не теряется | этап и время | не трогается | копится |
| `завершена` | разрешён (новый прогон) | разрешены | итог с находками | ставится, **только если блокеров нет И отпечатки совпали** | хранится до следующего старта; после правки статьи не пропадает, а помечается устаревшим (инвариант 5) |
| `сбой` | разрешён | разрешены | причина и находки | не трогается | хранится так же |

**`завершена` означает только то, что операция доработала до конца, а не то, что статья готова.**
Готовность ставится при двух условиях сразу: ни одной находки уровня блокер и отпечатки в конце
совпали с начальными. Отчёт показывается всегда — и когда готовность поставлена, и когда нет.

**Перезапуск сервера возвращает состояние `нет`**, барьер исчезает вместе с памятью. Отсюда
обязательное следствие: операция, начатая прошлым сервером, не может позже изменить ни готовность,
ни файлы статьи. Дочерние процессы прекращаются вместе с сервером, а переживший его результат не
применяется вовсе: он принадлежит задаче, которой в памяти уже нет.

**Инварианты.**
1. Одновременно идёт не более одной подготовки на статью; вторая получает отказ, а не очередь.
2. Пока подготовка идёт, ни одна запись в файлы этой статьи не проходит — ни сохранение, ни
   автосохранение. Ответственность делится: **сервер (это задание)** файл не меняет и отвечает
   отказом, который окно способно отличить от прочих ошибок; **окно (З1в)** держит несохранённый
   текст у себя и повторяет запись, когда барьер снят. Текст человека не теряется ни в одном звене.
3. Готовность ставится, только если отпечатки всех файлов статьи и всех файлов состояния в конце
   совпали с теми, что сняты в начале. Не совпали — готовности нет; подготовка не записывает ни файл
   статьи, ни файл состояния и говорит человеку, какие именно отпечатки разошлись. Сам файл при этом
   мог измениться — но не её рукой, и в этом вся разница.
4. Перезапуск сервера не оставляет статью запертой: барьер живёт в памяти и исчезает вместе с ней.
5. Отчёт принадлежит снимку: он описывает те байты, которые проверялись, и не переживает изменение
   файлов молча. **Правило устаревания:** на каждый запрос отчёта сервер сверяет нынешние отпечатки
   файлов статьи со снимком; разошлись — отчёт помечен устаревшим, готовность им подтвердить нельзя,
   и окно прямо говорит, что статья изменилась после проверки. Правку могли сделать мимо программы —
   в редакторе кода, через git, другим процессом, — поэтому сброса отчёта при своём сохранении мало.
6. **Отпечаток готовности переживает перезапуск сервера.** Отчёт и состояние операции живут в
   памяти и с перезапуском исчезают — доказательство того, что готовность отвечает нынешним байтам,
   исчезать не имеет права. Поэтому вместе с готовностью в файл состояния каждой существующей версии
   кладётся **отпечаток состава статьи**, по которому подготовка завершилась.
   **Что в него входит:** весь состав статьи из единственного правила ядра — все существующие
   языковые версии, их файлы состояния и картинки, а после З9 и файл комментариев.
   **Картинки у статьи, лежащей файлом, — открытый вопрос, и угадывать его запрещено.** Сегодня
   правило простое: картинка живёт рядом со своей статьёй (`SPEC.md` 1.3), вставка кладёт её в папку
   статьи, а удаление прямо отказывается работать, если в папке есть чужая статья, — «общие картинки,
   понять, что из этого чьё, нельзя» (`deleteArticle.mjs`). У статьи-файла папка общая с соседями,
   поэтому **картинки из неё её составом автоматически не считаются**. На сегодняшнем корпусе таких
   статей нет вовсе — все статьи лежат папками, — значит З0 это не задевает. **Правило принято и
   вопроса владельцу не требует:** состав статьи-файла — её файл версии, файлы состояния и, после З9,
   файл комментариев; картинки общей папки в него не входят. Расширить правило (например, считать
   картинки по ссылкам из текста) можно только отдельным словом владельца под доказанную нужду;
   отсутствие расширения работу не блокирует. Файлы состояния
   читаются канонически: служебные поля готовности и сам отпечаток из подсчёта исключаются, иначе
   запись отпечатка меняла бы то, что только что посчитали. Это решение, а не развилка: считать
   иначе — значит получить у двух сессий два разных отпечатка.
   **Как считается:** детерминированно по отсортированному перечню пар «нормализованный
   относительный путь — содержимое». Добавление, удаление, переименование файла и изменение любого
   байта меняют отпечаток; простая склейка содержимого без путей и границ запрещена — иначе
   переименование пройдёт незамеченным.
   **Где он сверяется:** перед тем как окно покажет публикацию доступной, и ещё раз перед коммитом
   (З3а). Не совпал или отсутствует вовсе — статья считается изменившейся после подготовки,
   публикация недоступна до нового прогона.
7. **Успешная подготовка создаёт отсутствующий файл состояния** существующей языковой версии по
   правилу З0: без него готовность и отпечаток хранить негде. При неуспехе, расхождении отпечатков
   или сбое ничего не создаётся.
8. **Готовность и отпечаток ложатся всем версиям разом или не ложатся никому.** Ошибка записи на
   второй версии из трёх не оставляет частичной готовности: либо у всех согласованные значения, либо
   каждый файл возвращён к прежнему виду побайтово, и человеку сказано.
9. **Устаревший отчёт закрывает публикацию.** Своя правка возвращает версию в черновик прежним
   правилом; правку мимо программы это правило не ловит, поэтому расхождение отпечатков со снимком
   само по себе делает «Опубликовать» недоступной до новой подготовки. Повторная проверка шапки в З3а
   качество и сборку не повторяет — за остальные байты отвечает именно сверка постоянного отпечатка.
   **Вердикт допуска публикации — один и живёт на сервере** (в этом задании), а не вычисляется
   заново окном или слоем git: они его спрашивают. В пределах З1б «публикация недоступна» значит, что
   этот вердикт отвечает запретом с причиной «статья изменилась после подготовки»; кнопка появится в
   З3а и обязана опираться на него. Сама запись готовности в файле при этом остаётся — действительной
   она считается только вместе с совпавшим отпечатком.

**Матрица сценариев.** Успех · находки есть, готовности нет · файл подменён во время операции ·
файл удалён во время операции · сохранение во время операции · повторный старт · перезапуск сервера
посреди операции · ошибка чтения файла · подготовка другой статьи параллельно (разрешена) ·
**статья изменена мимо программы после успешной подготовки** · **та же правка плюс перезапуск
сервера** · **ошибка записи второго файла состояния из трёх** · у одной версии файла состояния нет вовсе.

**Приёмка — обязательный минимум.** После успешной подготовки файл статьи изменён мимо программы —
публикация недоступна; сервер перезапущен — запрет остался (сверяется отпечаток из файла состояния,
а не память); новый успешный прогон обновляет отпечаток и снова разрешает публикацию.
Старт с отпечатком A, подмена файла на B до финала, все проверки
зелёные — готовности нет, файл состояния не тронут; сохранение во время подготовки — отказ словами,
файл не изменён; перезапуск сервера — «операции нет», готовность не поставлена; повторный старт —
отказ; подготовка второй статьи во время первой — разрешена и не мешает.
**Доказательства в инженерную запись.** Итог всех обязательных команд ворот · имена тестов по каждому сценарию
матрицы · ответы сервера в каждом состоянии.

### З1в. Окно подготовки

**Что сможет владелец.** Нажать «Подготовить», видеть ход, читать отчёт и по клику попадать к месту.
**Входит.** Кнопка и опрос хода; окно занято — переход к другой статье закрыт, автосохранение молчит;
отчёт с переходом к месту, включая переход к нужной языковой версии и раскрытие свойств на нужном
поле (сегодня свойства раскрываются только сами по себе — нужен управляемый режим); надписи находок
заводятся в настройках вместе с окном; ненавязчивая просьба заполнить ключевые слова при открытии
статьи; ответ сохранения возвращает окну исправленную шапку — закрываются два хвоста про расхождение
окна с диском; подготовка выносится своим модулем, а не доливается в файл окна на пределе размера.
**Не входит.** Внешние этапы · галочки версий · свёртка отчётов.
**Приёмка.** В любой момент подготовки на экране названы идущий этап и прошедшее время, смена этапа
видна без действий человека; клик по находке открывает нужную версию и ставит курсор в поле или
строку; **отчёт честно перечисляет этапы, которые не выполнялись** (до З2 это проверка качества и
сборка — строкой «не проверялось», а не молчанием); свежесозданная статья с заполненным описанием
проходит, хотя у заглушки нет ключевых слов, и в отчёте про это предупреждение; после сохранения
с защитной правкой поле в свойствах совпадает с файлом без переоткрытия статьи; перезагрузка страницы
во время подготовки не теряет операцию — окно снова показывает её ход, а не пустой экран.
**Инварианты.** Окно никогда не показывает готовность, которой нет на диске. Отчёт описывает тот
снимок, по которому считался, и не переживает изменение файлов молча. Переход по находке ведёт к
существующему месту либо честно сообщает, что место исчезло.
**Матрица сценариев.** Отчёт без находок · только предупреждения · блокеры · находка без места
(красная сборка) · находка в соседней языковой версии · статья изменилась во время подготовки ·
уход из статьи во время подготовки · перезагрузка страницы во время подготовки.
**Доказательства в инженерную запись.** Запись живой проверки по шагу 6 · снимок экрана отчёта, а где среда его
не умеет — дословная выписка надписей с экрана · что показано в момент каждого этапа.

### З2. Внешние этапы: проверка качества и полная сборка

**Что сможет владелец.** Зелёная подготовка означает «сборка сайта это переживёт».
**Входит.** Дочерние процессы самим `node`, без оболочки, прямым путём к сборщику; таймаут —
настройка; отбор находок по точным путям версий с отделением номера строки; «проверено 0 файлов»
при непустой статье — блокирующий сбой этапа; красная сборка по чужой вине — прямые слова и хвост
лога; внешние этапы не запускаются, если блокеры уже найдены.
**Не входит.** Разбор вывода сборщика в структурные находки (отказ записан) · починка чужих статей.
**Приёмка.** Подложный ответ «проверено 0» даёт блокер; находка по соседней статье с похожим путём
в отчёт не попадает; живая проверка идёт на пробной статье в настоящих папках сайта (песочницу
проверка качества не видит — ложный зелёный), статья убирается до отчёта; строка «не проверялось»
из отчёта исчезает.
**Инварианты.** Дочерний процесс всегда завершается: по своему концу или по таймауту, и второй
случай — находка, а не тишина. Нулевой код возврата сам по себе зелёным этапом не считается: разбор
ответа обязателен. Находки чужих статей в отчёт статьи не попадают.
**Матрица сценариев.** Всё зелено · находки проверки качества · красная сборка по этой статье ·
красная сборка по чужой статье · таймаут · процесс не запустился · «проверено 0 файлов» · статья в
песочнице (подготовка недоступна, кнопка говорит почему).
**Доказательства в инженерную запись.** Хвост лога сборки · время каждого этапа · запись живой проверки на
пробной статье в настоящих папках и подтверждение, что она убрана.

### З3а. Публикация: коммит по перечню с подтверждением состава

**Что сможет владелец.** Нажать «Опубликовать», увидеть состав настоящего коммита, отказаться без потерь.
**Входит.** Слой записи git с нуля — сегодня git только читается: добавление по явному перечню путей,
коммит, снятие коммита, проверка ветки и чистоты индекса, список отличий от опубликованной ветки одним
запросом; состав статьи правилом ядра (все версии, файлы состояния, картинки; добавленные,
изменённые, удалённые, переименованные); никогда «добавить всё» и никогда «коммит со всеми правками»;
повторный прогон блокирующих проверок шапки по фактическим файлам до коммита; **сверка отпечатка состава с тем, что сохранила успешная подготовка** — не совпал или отсутствует, публикация останавливается и зовёт пройти подготовку заново; «Опубликовать» активна
только при готовности всех существующих версий; барьер операции на сервере и в окне; демонтаж поля
опубликованного коммита во всех четырёх местах — готовность «Опубликована» выводится из ветки.
**Не входит.** Отправка (З3б) · откат кнопкой · галочки версий.
**Приёмка.** Во временном репозитории лежат чужие изменённые и чужие новые файлы; коммит статьи
содержит ровно перечень состава и ничего сверх; отказ вернул ветку, рабочее дерево цело; ветка
разошлась с опубликованной — остановка словами до коммита; видимость сняли в файле мимо программы —
публикация останавливается и зовёт пройти подготовку.
**Инварианты.** В коммит попадают только пути из состава статьи — ни одним файлом больше, чем бы
ни было в рабочем дереве. **Условия старта, проверяемые ДО коммита:** текущая ветка — `main`, её
вершина совпадает с `origin/main`, индекс пуст. Отстала, обогнала, разошлась или индекс не пуст —
публикация не начинается, и программа ничего не выправляет сама. Совпадение проверяется именно до
коммита: после него локальная ветка обгоняет опубликованную на один коммит, и это нормально.
Сведения об опубликованной ветке перед этой проверкой обновляются явным чтением с сервера (без
слияния: молчаливые `pull` и `rebase` запрещены); прочитать не удалось — публикация не начинается и
говорит почему, а не полагается на устаревшую запись.
**Отказ человека возвращает репозиторий к прежнему состоянию** — та же вершина, тот же индекс, то же
рабочее дерево побайтово; чужие изменения при этом не трогаются вовсе. Готовность и файлы человека
при отказе не меняются.
**Матрица сценариев.** Чистое дерево · чужие изменённые файлы · чужие новые файлы · сведения об
опубликованной ветке устарели или недоступны · ветка отстала ·
ветка обогнала · индекс не пуст · видимость правлена мимо программы · отказ человека · повторное
нажатие · сбой git посреди операции.
**Доказательства в инженерную запись.** Состав настоящего коммита (`git show --name-only`) · состояние ветки до
и после · итог тестов на настоящем git.
**Шаги (делить по границам модулей, а не по времени).** 1) правило состава статьи с тестами · 2) слой
записи git на временном репозитории · 3) серверная операция и барьер · 4) окно подтверждения состава ·
5) сквозной сценарий целиком. Каждый шаг оставляет репозиторий зелёным и имеет свой машинный контракт;
живая проверка — на шагах 4 и 5.

### З3б. Публикация: отправка и слежение. **Первая живая статья**

**Что сможет владелец.** Выпустить статью на сайт из программы, при себе.
**Входит.** Отправка только явным `origin main`; повтор того же коммита без переписывания истории;
«ветка обогнала» — остановка словами; статусы «отправлено → сборка идёт → зелёная или красная со
ссылкой → на сайте»; «на сайте» — обе работы зелёные и страница отвечает; откат назван заранее.
**Не входит.** Автоповтор со счётчиком · кнопка отката · разрешение конфликтов.
**Приёмка.** Обе работы зелёные по коммиту статьи → статья открывается по своему адресу → описание на
месте, скрытая версия не торчит в меню, переключатель языков не ведёт в пустоту → главная и одна
старая статья открываются как прежде.
**Инварианты.** Отправка идёт только явным `origin main`. Повтор отправляет тот же коммит и не
создаёт второго. История не переписывается никогда. «На сайте» ставится только по факту: обе работы
зелёные и страница отвечает.
**Матрица сценариев.** Успех · обрыв сети · ветка обогнала · красная сборка · зелёная сборка, но
страница не отвечает · повторное нажатие · закрытие окна во время слежения.
**Доказательства в инженерную запись.** Ссылка на запуск сборки · адрес живой страницы · снимок состояния окна
на каждом шаге.
**Точка остановки:** перед самой отправкой — показать ветку, коммит, перечень файлов, итог ворот и
ждать отдельного «да» владельца.

## Группа 3. Быстрее и приятнее — по желанию владельца

Одна обложка вместо двух · дата календарём и метки множественным выбором · автосжатие картинок ·

## Решения владельца 2026-08-11. Вопросов больше нет

Пять прежних вопросов закрыты его словом: по ним останавливаться больше не нужно. Точки обязательной
остановки из шага 8 при этом остаются в силе — они про другое. Полные формулировки — `BUSINESS.md`,
раздел 7в.

1. **Шесть статей без описания не трогаем.** Он допишет сам, когда откроет их. Исключения для старых
   статей не заводим: подготовка попросит заполнить, и это нормально.
2. **Удаление переносит статью в архив, и оттуда её можно вернуть** (задание З13). Временно снять
   статью с глаз — режим «только по ссылке». **Переадресации со старых адресов не создаются вовсе** —
   они уходят из плана: З7 переносит статью между разделами без них, старая ссылка перестаёт
   работать. Безвозвратного удаления нет ни у программы, ни у человека в окне.
3. **Статья-файл внутри раздела — обычная статья.** Поля, которых нет, стоят в окне пустыми; лишнее
   поле даёт предупреждение, убирает его человек сам в файле. Категорию «Добро пожаловать» назначаем
   явно (задание З16). **Инвариант, обязательный для З16 и для всякой работы с полями:** открытие
   статьи ничего не дописывает в файл — пустое поле попадает туда, только когда человек его заполнил,
   а лишнее поле программа не удаляет сама никогда.
4. **Скрипт переноса из Word не трогаем.** Возможен позже импорт из Word отдельной возможностью —
   в группу 3, без срока.
5. **Программа — полноценная CMS:** создание, правка и удаление делаются в ней целиком, включая блог.
   Строка бизнес-карты про «блог пока не создаётся» исправлена зачёркиванием со сноской.

## Словарь. Одно слово — один смысл

Термины ниже употребляются только в этом значении; сессия, которая поняла иначе, ошиблась.

- **Живая статья** — статья, лежащая в папках контента сайта (`docs`, `blog`, `i18n`), а не в
  песочнице `editor/sandbox`.
- **Языковая версия (существующая)** — файл статьи, лежащий на диске в корне своей локали. Версия,
  которой на диске нет, не существует; заглушка существует.
- **Видимая версия** — та, у которой в шапке нет `unlisted: true`. **Скрытая** — та, у которой оно
  есть. Скрытая существует и попадает в публикацию.
- **Готовность** — «Черновик» или «Готова к публикации» в файле состояния версии, либо
  «Опубликована», выведенная из опубликованной ветки. Принадлежит версии, а не статье.
- **Опубликованная ветка** — `origin/main` репозитория сайта.
- **Состав статьи** — правило ядра: все существующие языковые версии, их файлы состояния,
  принадлежащие статье картинки, а после З9 — файл комментариев. **Принадлежность картинок:** у
  статьи, единственной в своей папке, это картинки её папки; у статьи, лежащей файлом в общей папке,
  картинки папки в состав НЕ входят — её состав это файл версии, файлы состояния и, после З9, файл
  комментариев. Единственное место правила; снимок, отпечатки, коммит и уборка берут состав только у
  него. **Такого правила в коде пока нет — оно заводится в З1б;** сегодня есть только
  `путиДругихВерсий`, знающая одни версии.
- **Файл состояния** — служебный файл языковой версии, где живёт её готовность и отпечаток состава, по которому эта готовность поставлена. Сегодня в нём есть
  ещё поле опубликованного коммита (демонтируется в З3а) и пустое место под нити комментариев.
  **Комментарии там жить не будут:** с З9 они лежат в отдельном файле комментариев статьи, и если к
  тому времени в состоянии окажутся записанные нити, З9 переносит их вместе с собой.
- **Род** — блог или документация: чем страница является для сайта и какие поля он у неё покажет.
  Задан движком, программа его не выбирает.
- **Категория** — урок, семейство, курс, справка, блог, документация, статья-описание раздела: выбор
  владельца. **Требования к полям задаются по категории, а не по роду.**
- **Статья-описание раздела** — страница, открывающая раздел меню (в коде и старых записях —
  «страница раздела», «служебная страница»). Слово «обложка» к ней не применяется: обложка — это
  картинка статьи.
- **Настоящая находка** — замечание с доказательством: путь к месту в коде, воспроизведение, цитата
  документа или красный тест. Мнение без доказательства находкой не считается.
- **Защитная правка** — исправление шапки, которое программа делает сама при сохранении, без
  действия человека, и только там, где иначе падает сборка сайта.
- **Машинный слой** — цвет, которым помечен текст, изменённый программой, а не человеком и не ИИ.
- **Лента версий** — полоса снимков статьи, свёрнутых по сеансам одного автора.
- **Корпусный прогон** — проход по всем файлам контента с проверкой «поведение до и после правки
  одинаково»; в отчёт идут число проверенных файлов и число изменившихся.
- **Работы зелёные** — обе работы GitHub Actions по коммиту публикации закончились успехом.
- **Страница отвечает по своему адресу** — запрос по адресу из шапки статьи возвращает 200 и
  содержит её заголовок.
- **Архив** — папка вне сборки сайта, куда уходит удалённая статья целиком: все языковые версии,
  файлы состояния и картинки. Из архива статью можно вернуть обратно; стереть её безвозвратно
  программа не умеет и уметь не должна. **История версий физически лежит отдельно**
  (`editor/.history`), поэтому «уходит в архив» для неё значит другое: связь истории со статьёй
  обязана пережить и архивирование, и возврат, а как это сделано — решает лист задания З13.
