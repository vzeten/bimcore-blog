# Обязательные правила программы

> Только техника: чего нельзя нарушать и как должен быть устроен код.
> Поведение программы описано в `BUSINESS.md` — при расхождении верен он.
> Порядок работ — в `PLAN.md`.

---

## 1. Контекст проекта

1.1. Сайт learn.bimcore.one: Docusaurus 3.10.1, MDX 3, React 19, Node ≥20.
1.2. Репозиторий `https://github.com/vzeten/bimcore-blog`, публичный. Хостинг GitHub Pages, развёртывание через `.github/workflows/deploy.yml`. Отправка в `main` = публикация.
1.3. Статья — папка `<slug>/index.mdx`. Картинки рядом со статьёй или в `img/` рядом с ней.
1.4. Пути: EN — `docs/` и `blog/`; RU — `i18n/ru/docusaurus-plugin-content-docs/current/` и `i18n/ru/docusaurus-plugin-content-blog/`; ES — так же в `i18n/es/`.
1.5. Прежней CMS в проекте нет. Её защитные правила перечислены в `DECISIONS.md` — они обязательны и должны работать в редакторе.

## 2. Инварианты сайта. Нарушение роняет сборку целиком

2.1. Поле `image` либо содержит корректный путь, либо отсутствует. Пустое значение роняет сборку.
2.2. Имена файлов картинок — латиница, цифры, дефис. Пробел или кириллица роняют сборку.
2.3. `onBrokenLinks: 'throw'` и `onBrokenMarkdownLinks: 'throw'`: одна битая ссылка роняет сборку.
2.4. Статья, лежащая только в русской папке без английского двойника, не попадает в сборку вообще — молча, без ошибки. Английская заглушка обязательна.
2.5. `slug` общий для всех языков, после публикации не меняется без 301-редиректа. Для документации — абсолютный с префиксом раздела, для блога — относительный.
2.6. `sidebars.js` руками не трогать: боковое меню строится из файловой системы.
2.7. Файлы и папки, имя которых начинается с подчёркивания, Docusaurus не собирает. Служебные файлы программы класть только так.

2.8. Видимость статьи (`unlisted`) — поле её шапки и ничего больше. Строку `unlisted` пишет ровно одно правило ядра (`setUnlisted`): второй писатель, будь то отдельная ручка, общий сбор полей или создание статьи, считается дефектом приёмки (SPEC 4.3). ~~Видимость применяется ко всем существующим языковым версиям сразу.~~ **Исправлено словом владельца 2026-08-10:** видимость принадлежит языковой версии, сохранение меняет её только в открытом файле, расхождение версий — нормальное состояние. Код приводится в соответствие кругом 1б (`CURRENT_TASK.md`).

## 3. Технические запреты и обязательный выбор

3.1. Редактор текста — CodeMirror 6, оформление накладывается поверх исходного MDX.
3.2. Запрещены ProseMirror, Tiptap, Slate и любое преобразование MDX в промежуточное дерево с обратной сборкой: они теряют разметку.
3.3. Блочные замены строк объявлять только через состояние редактора, плагину это запрещено самим CodeMirror.
3.4. Внешних отступов у строк редактора быть не должно: CodeMirror считает по ним высоту и промахивается при клике. Только внутренние.
3.5. Все файлы UTF-8. Переводы строк массово не менять: если текст не изменился, файл не переписывается вовсе.
3.6. Сравнение текстов не должно зависеть от переводов строк: на диске файл может быть в windows-виде, а в git — в unix-виде.
3.7. Разбиение текста на слова — собственное. Готовые библиотечные сравнения слов не знают кириллицы и режут русские слова по буквам.

## 4. Устройство кода

4.1. TypeScript, строгий режим. Проверка типов — `npm run editor:typecheck`, обязательна перед сдачей задания. Тесты — vitest.
4.2. Ядро отделено от интерфейса: модель документа, слои цвета, якоря, сравнение, git, проверки — модули без обращения к интерфейсу.
4.3. Одно правило — одно место. Дублирование правила в двух местах считается дефектом приёмки.
4.4. **Значение живёт в настройках, если его может захотеть изменить человек, не переписывая программу.** Проверочный вопрос один: кто решит, что оно станет другим — владелец или переделка кода? Владелец — значит настройка.
   В настройках: пути к контенту, языки и основной язык, категории, цвета и их смысл, статусы, видимость, команды панели, все надписи, пороги и размеры, форматы дат, шаблоны имён, адреса и ссылки, имена служебных файлов, интервалы и число повторов.
   В коде остаются только четыре вида значений: имена полей чужих форматов, которые задали не мы (`image` и `slug` заданы Docusaurus), синтаксис markdown, внутренний договор между сервером и интерфейсом одной программы, технические величины алгоритмов. Каждая такая величина получает имя и объяснение, почему она не настройка.

4.4.1. Умолчания в коде, повторяющие настройку, запрещены. Умолчание создаёт второй источник правды и срабатывает молча, когда настройку забыли передать: в настройках основной язык поменяли, а программа продолжает работать по забытому умолчанию.

4.4.2. Настройка, которую код не читает, — дефект: она выглядит рабочей и обманывает. Перед сдачей задания каждый ключ настроек либо используется, либо удаляется. Проверяется машиной: тест обходит ключи настроек и ищет каждый в коде. Ключ, заведённый заранее «под будущее задание», считается таким же дефектом — он появляется вместе с кодом, который его читает.

4.5. Правила проверки задаются по категориям статей и меняются без правки кода.

4.5.1. Цвет несёт единственный смысл — слой правок (кто менял текст). Больше ничему цвет не отдаётся. Ссылка обозначается подчёркиванием и наследует цвет своего слоя, а не собственным цветом: иначе синий ссылки спорит с синим нового текста. Это стиль оформления, а не настройка.

4.5.2. Две первые стадии готовности («Черновик», «Готова к публикации») живут в файле состояния: их ставит человек или подготовка. Последняя стадия («Опубликована») не хранится никогда и выводится из факта публикации: файл есть в опубликованной ветке и совпадает с диском — «Опубликована», и это перебивает записанное в состоянии; есть, но отличается — показывается записанная стадия, потому что правка ещё не уехала; нет в ветке вовсе — тоже записанная, а без файла состояния «Черновик». Слепое «Черновик» для уже вышедших статей запрещено. «Опубликована» означает «уехала в репозиторий сайта», а не «уже видна людям»: живая страница появляется после зелёной сборки и показывается отдельной строкой состояния публикации. Признак «есть в опубликованной ветке» и признак «совпадает с ней» разные и не подменяют друг друга: первый решает, можно ли удалять статью, второй — готовность. Порядок статусов в настройках — стадии по времени (первый — черновик, последний — опубликована), это договор, а не случайность.

4.5.3. Служебная страница раздела (index-файл раздела меню, у которого есть вложенные статьи) получает отдельную категорию из настроек, а не «документация». Признак структурный, а не по имени файла.
4.6. Всё, что можно, — чистые функции без побочных действий: раскраска, якоря, сравнение, нормализация имён, разбор файла статьи.
4.7. Внешний мир — через тонкие адаптеры: файловая система, git, GitHub, буфер обмена, запуск команд.
4.8. Данные текут в одну сторону: диск → ядро → интерфейс. Интерфейс не пишет в файлы напрямую.
4.9. Размер файла кода — не больше 300 строк. Правило про читаемость, поэтому касается кода: `.ts`, `.tsx`, `.mjs`, `.css` в `src/`, `tests/` и `server.mjs`. Проверяется машиной, а не на глаз.

4.9.1. Файлы данных под это правило не подпадают: `settings.json` читается человеком как единый справочник, и дробление его на части создало бы вопрос «в каком файле искать» и второй источник правды. Ограничение размера ему не помогает — помогает порядок разделов и пояснения `_` рядом с ключами.
4.10. Список зависимостей фиксированный: TypeScript, CodeMirror 6, React 19, Vite, gray-matter, diff, simple-git, vitest. Новая — только с обоснованием в `DECISIONS.md`.
4.11. Белый экран вместо программы недопустим: при сбое показывается причина словами.

4.12. **Обработка ошибок закладывается при создании каждого метода, а не потом.** Полный стандарт — раздел «6. Обработка ошибок»; он обязателен для любого метода, трогающего внешний мир (сеть, файлы, git, разбор JSON, ввод пользователя).

## 5. Обязательные проверки

5.1. Открыть статью и сохранить без правок — файл не меняется ни на байт. Проверяется на всех статьях сайта, а не на выборке, и именно тем путём, которым сохраняет сервер: шапка собирается заново, а не приклеивается исходным куском. Проверка «разобрал и склеил обратно» пропускает целый класс поломок.
5.2. У каждого правила есть свой тест, и **имя теста повторяет формулировку правила**. Отдельного списка правил не ведётся: список — это вывод `npm run editor:test`, он не может разойтись с кодом. Рукописная таблица «правило → файл» запрещена: она устаревает в тот же день.

5.2.1. Тест проверяет результат функции или запроса, а не наличие строки в коде. Структурные тесты (поиск подстроки в исходнике: «настройка читается кодом», «файл не длиннее 300 строк», «реестр не пишет файлы») допустимы только как предохранители от регресса, а не как доказательство поведения; где поведение можно проверить результатом — проверяем результатом.
5.3. Быстрые проверки при каждом сохранении укладываются в доли секунды: метаданные валидны, `image` без пробелов и не пустой, пути картинок существуют, MDX разбирается, внутренние ссылки целы.
5.4. Полная сборка сайта — обязательный шаг подготовки к публикации.

## 6. Обработка ошибок

Стандарт обязателен. Пишется вместе с методом, а не добавляется потом.

6.1. **Одна дверь к серверу.** Все запросы интерфейса идут через общий помощник `requestJson`. Прямой `fetch` в компонентах и действиях интерфейса запрещён.

6.2. **`requestJson` обязан:** проверить `response.ok`; безопасно прочитать JSON; при ошибке взять текст из `{error}` ответа; если сервер вернул не JSON — дать понятное сообщение; бросить нормальную ошибку с текстом для человека.

6.3. **Сервер всегда отвечает на API JSON-ом.** Формат ошибки единый: `{ "error": "человеческий текст" }`. HTML-страница ошибки, сырой stack trace и пустой ответ для API запрещены.

6.4. **Ожидаемые ошибки — с правильным кодом:** 400 — плохой запрос или битый JSON; 404 — нет статьи, картинки, файла; 409 — конфликт (файл изменился снаружи); 500 — внутренняя ошибка. Предел размера тела — тоже плохой запрос (400).

6.5. **Внутренняя ошибка видна, но без простыни.** Сервер пишет её в `console.error`, пользователю отдаёт короткий понятный текст без стека.

6.6. **Интерфейс не меняет состояние, пока сервер не подтвердил успех.** `save()` не показывает «Сохранено» и не сбрасывает признак несохранённого при ошибке; `pasteImage()` не вставляет `![](undefined)`; `replaceImage()` не перезагружает страницу, если файл не заменён. Видимость отдельного действия не имеет вовсе: она обычное поле шапки, и при отказе сохранения остаётся несохранённой правкой в окне, как заголовок или описание.

6.7. **Ошибка показывается спокойно и заметно:** без `alert` для обычных ошибок; текстом рядом с действием или в общей строке; не перекрывая статью; человек понимает, что именно не вышло; набранный текст остаётся на месте.

6.8. **Белый экран — последняя защита.** React Guard нужен, но обычные ошибки сохранения, загрузки, видимости и картинок ловятся до падения всего интерфейса, а не им.

6.9. **`readBody` безопасен:** битый JSON не роняет сервер; слишком большое тело отклоняется; ошибка чтения тела возвращает JSON 400.

6.10. **Тексты ошибок — в `settings.json`.** Всё, что видит человек и может меняться, живёт в настройках; в коде — только технические коды и внутренние имена.

6.11. **Тесты проверяют поведение, а не строки в коде.** Обязательный минимум: битый JSON → 400 JSON-ошибка; `save` при 500 не сбрасывает `dirty` и не показывает «Сохранено»; сохранение при 500 не меняет показанную видимость; `pasteImage` при ошибке не вставляет markdown; `replaceImage` при ошибке не перезагружает страницу; API отдаёт JSON-ошибку на ожидаемые сбои.

6.12. Полный «Отчёт об ошибке» с переходом к месту в статье — это В1-18. Раздел 6 — обязательный минимум, который есть уже сейчас, до автосохранения.

## 7. Запуск

7.1. Команда `npm run editor:dev`, адрес `http://localhost:4780`. Порт задаётся в `settings.json`.
7.2. Сервер запускается напрямую, без сборки. Интерфейс собирается на лету.
7.3. Программа работает без интернета. Сеть нужна только для проверки удалённого репозитория, публикации и чтения состояния развёртывания.

## 8. Что уже есть в проекте и переиспользуется

8.1. `npm run content:check` — `scripts/content-check.js`, машинные правила качества в `content-quality-rules.json`.
8.2. `npm run review` — `scripts/review-page.js`, страница показа правок по git-диффу. Палитра там своя, к слоям редактора не приведена.
8.3. `scripts/word2mdx.js` — перенос статей из Word.
8.4. Карта видео `static/video-sitemap.xml` ведётся вручную и объявлена в `robots.txt`. Карты статей создаются движком сами.

## 9. Сопутствующие документы

- `BUSINESS.md` — зачем программа и что должен уметь человек. Главнее этого файла в вопросах поведения.
- `PLAN.md` — вехи, декомпозиция и статусы работ.
- `DECISIONS.md` — журнал решений и защитные правила, спасённые из прежней CMS.
- `CURRENT_TASK.md` — карточка текущего задания с критериями приёмки. Всегда одно задание, без статусов и истории.
