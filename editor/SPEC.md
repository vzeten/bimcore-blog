# Обязательные правила программы

> Только техника: чего нельзя нарушать и как должен быть устроен код.
> Поведение программы описано в `BUSINESS.md` — при расхождении верен он.
> Порядок работ — в `TASKS.md`.

---

## 1. Контекст проекта

1.1. Сайт learn.bimcore.one: Docusaurus 3.10.1, MDX 3, React 19, Node ≥20.
1.2. Репозиторий `https://github.com/vzeten/bimcore-blog`, публичный. Хостинг GitHub Pages, развёртывание через `.github/workflows/deploy.yml`. Отправка в `main` = публикация.
1.3. Статья — папка `<slug>/index.mdx`. Картинки рядом со статьёй или в `img/` рядом с ней.
1.4. Пути: EN — `docs/` и `blog/`; RU — `i18n/ru/docusaurus-plugin-content-docs/current/` и `i18n/ru/docusaurus-plugin-content-blog/`; ES — так же в `i18n/es/`.
1.5. Прежней CMS в проекте нет. Её защитные правила перечислены в `DECISIONS.md` — они обязательны и должны работать в редакторе.

## 2. Инварианты сайта. Нарушение роняет сборку целиком

2.1. Поле `image` либо содержит корректный путь, либо отсутствует. Пустое значение роняет сборку.
2.2. Имена файлов картинок — латиница, цифры, дефис. Пробел или кириллица роняют сборку.
2.3. `onBrokenLinks: 'throw'` и `onBrokenMarkdownLinks: 'throw'`: одна битая ссылка роняет сборку.
2.4. Статья, лежащая только в русской папке без английского двойника, не попадает в сборку вообще — молча, без ошибки. Английская заглушка обязательна.
2.5. `slug` общий для всех языков и после публикации не меняется. **Уточнено словом владельца 2026-08-11:** переадресаций программа не создаёт вовсе; перенос статьи между разделами меняет адрес, программа предупреждает об этом заранее, а старая ссылка перестаёт работать. Для документации — абсолютный с префиксом раздела, для блога — относительный.
2.6. `sidebars.js` руками не трогать: боковое меню строится из файловой системы.
2.7. Файлы и папки, имя которых начинается с подчёркивания, Docusaurus не собирает. Служебные файлы программы класть только так.

2.7.1. **Редакционные данные в репозиторий сайта не кладутся вовсе** (решение владельца 2026-08-15). Замечания к фрагментам, ответы ИИ, переписка о статье и прочая внутренняя кухня — не контент: репозиторий сайта публичный, и подчёркивание в имени прячет файл от сборки, но не от чужих глаз. **Запрет действует уже сейчас; место хранения выбрано направлением, а не устройством:** отдельный **приватный** репозиторий редакционных данных на GitHub, своего сервера программа не заводит. Формат файлов, их размещение и порядок синхронизации этим пунктом не задаются — они выбираются перед реализацией комментариев и тогда же записываются. Правило касается только редакционных данных: готовность версии и прочее служебное состояние живут по прежним правилам.

2.8. Видимость (`unlisted`) — поле шапки и ничего больше. Строку `unlisted` пишет ровно одно правило ядра (`setUnlisted`): второй писатель, будь то отдельная ручка, общий сбор полей или создание статьи, считается дефектом приёмки (SPEC 4.3).

2.8.1. **Видимость принадлежит языковой версии, а не статье целиком** (слово владельца 2026-08-10, круг 1б сделан). Сохранение меняет её только в открытом файле: соседние версии не трогаются ни записью, ни снимком в истории, ни готовностью. Разная видимость версий — нормальное состояние, а не рассинхрон: так уже живут три статьи сайта, где русская версия в меню, а английская скрыта. Скрытая версия остаётся существующей для правила 2.4 и для удаления (В3-05): скрытая — значит не показанная в меню, а не отсутствующая. Признак «изменение ещё не на сайте» считается по открытой версии; названная плата — расхождение соседней версии с сайтом видно только после её открытия.

## 3. Технические запреты и обязательный выбор

3.1. Редактор текста — CodeMirror 6, оформление накладывается поверх исходного MDX.
3.2. Запрещены ProseMirror, Tiptap, Slate и любое преобразование MDX в промежуточное дерево с обратной сборкой: они теряют разметку.
3.3. Блочные замены строк объявлять только через состояние редактора, плагину это запрещено самим CodeMirror.
3.4. Внешних отступов у строк редактора быть не должно: CodeMirror считает по ним высоту и промахивается при клике. Только внутренние.
3.5. Все файлы UTF-8. Переводы строк массово не менять: если текст не изменился, файл не переписывается вовсе.
3.6. Сравнение текстов не должно зависеть от переводов строк: на диске файл может быть в windows-виде, а в git — в unix-виде.
3.7. Разбиение текста на слова — собственное. Готовые библиотечные сравнения слов не знают кириллицы и режут русские слова по буквам.

## 4. Устройство кода

4.1. TypeScript, строгий режим. Проверка типов — `npm run editor:typecheck`, обязательна перед сдачей задания. Тесты — vitest.
4.2. Ядро отделено от интерфейса: модель документа, слои цвета, якоря, сравнение, git, проверки — модули без обращения к интерфейсу.
4.3. Одно правило — одно место. Дублирование правила в двух местах считается дефектом приёмки.
4.4. **Значение живёт в настройках, если его может захотеть изменить человек, не переписывая программу.** Проверочный вопрос один: кто решит, что оно станет другим — владелец или переделка кода? Владелец — значит настройка.
   В настройках: пути к контенту, языки и основной язык, категории, цвета и их смысл, статусы, видимость, команды панели, все надписи, пороги и размеры, форматы дат, шаблоны имён, адреса и ссылки, имена служебных файлов, интервалы и число повторов.
   В коде остаются только четыре вида значений: имена полей чужих форматов, которые задали не мы (`image` и `slug` заданы Docusaurus), синтаксис markdown, внутренний договор между сервером и интерфейсом одной программы, технические величины алгоритмов. Каждая такая величина получает имя и объяснение, почему она не настройка.

4.4.1. Умолчания в коде, повторяющие настройку, запрещены. Умолчание создаёт второй источник правды и срабатывает молча, когда настройку забыли передать: в настройках основной язык поменяли, а программа продолжает работать по забытому умолчанию.

4.4.2. Настройка, которую код не читает, — дефект: она выглядит рабочей и обманывает. Перед сдачей задания каждый ключ настроек либо используется, либо удаляется. Проверяется машиной: тест обходит ключи настроек и ищет каждый в коде. **Служебные команды (`editor/scripts/`) в этот обход не входят намеренно**, хотя кодом программы считаются (4.9): настройка, которую читает одна такая команда, иначе выглядела бы живой, а человеку в окне не давала бы ничего. Ключ, заведённый заранее «под будущее задание», считается таким же дефектом — он появляется вместе с кодом, который его читает.

4.5. Правила проверки задаются по категориям статей и меняются без правки кода.

4.5.1. Цвет несёт единственный смысл — слой правок (кто менял текст). Больше ничему цвет не отдаётся. Ссылка обозначается подчёркиванием и наследует цвет своего слоя, а не собственным цветом: иначе синий ссылки спорит с синим нового текста. Это стиль оформления, а не настройка.

4.5.2. Две первые стадии готовности («Черновик», «Готова к публикации») живут в файле состояния: их ставит человек или подготовка. Последняя стадия («Опубликована») не хранится никогда и выводится из факта публикации: файл есть в опубликованной ветке и совпадает с диском — «Опубликована», и это перебивает записанное в состоянии; есть, но отличается — показывается записанная стадия, потому что правка ещё не уехала; нет в ветке вовсе — тоже записанная, а без файла состояния «Черновик». Слепое «Черновик» для уже вышедших статей запрещено. «Опубликована» означает «уехала в репозиторий сайта», а не «уже видна людям»: живая страница появляется после зелёной сборки и показывается отдельной строкой состояния публикации. Признак «есть в опубликованной ветке» и признак «совпадает с ней» разные и не подменяют друг друга: первый решает, можно ли удалять статью, второй — готовность. Порядок статусов в настройках — стадии по времени (первый — черновик, последний — опубликована), это договор, а не случайность.

4.5.3. Служебная страница раздела (index-файл раздела меню, у которого есть вложенные статьи) получает отдельную категорию из настроек, а не «документация». Признак структурный, а не по имени файла.
4.5.4. Порядок и отбор реестра — чистые правила `core/siteOrder.mjs` и `core/registry.mjs` над сводом сервера. Дату ленты (`date` шапки, по UTC, как читает Docusaurus) и номер меню сервер отдаёт готовыми полями строки (`дата` версии, `порядокМеню`); окно по файлам не ходит. Отборы считаются теми же признаками, что красят буквы локалей (`признакиЛокали`); неизвестное состояние публикации статью из «Есть что опубликовать» не убирает.
4.6. Всё, что можно, — чистые функции без побочных действий: раскраска, якоря, сравнение, нормализация имён, разбор файла статьи.
4.7. Внешний мир — через тонкие адаптеры: файловая система, git, GitHub, буфер обмена, запуск команд.
4.8. Данные текут в одну сторону: диск → ядро → интерфейс. Интерфейс не пишет в файлы напрямую.
4.9. Размер файла кода — не больше 300 строк. Правило про читаемость, поэтому касается кода: `.ts`, `.tsx`, `.mjs`, `.css` внутри папки редактора — `editor/src/`, `editor/tests/`, `editor/scripts/` и `editor/server.mjs`. Скрипты сайта в корневой папке `scripts/` (см. 8.1–8.3) под это правило не подпадают: они старше программы и живут своей жизнью. Проверяется машиной, а не на глаз.

4.9.1. Файлы данных под это правило не подпадают: `settings.json` читается человеком как единый справочник, и дробление его на части создало бы вопрос «в каком файле искать» и второй источник правды. Ограничение размера ему не помогает — помогает порядок разделов и пояснения `_` рядом с ключами.
4.10. Список зависимостей фиксированный: TypeScript, CodeMirror 6, React 19, Vite, gray-matter, js-yaml, diff, simple-git, vitest. Новая — только с обоснованием в `DECISIONS.md`.

4.10.1. **Ядро общее для сервера и окна, поэтому библиотека для Node в нём запрещена.** `gray-matter` написан под Node (требует `Buffer`) и в окне падает целиком; значение поля шапки читает `js-yaml` — тот самый разбор, который `gray-matter` вызывает внутри. Обоснование — в `DECISIONS.md`. Проверяется живой проверкой в окне: машинные тесты идут в Node и такой поломки не видят вовсе.
4.11. Белый экран вместо программы недопустим: при сбое показывается причина словами.

4.12. **Обработка ошибок закладывается при создании каждого метода, а не потом.** Полный стандарт — раздел «6. Обработка ошибок»; он обязателен для любого метода, трогающего внешний мир (сеть, файлы, git, разбор JSON, ввод пользователя).

## 5. Обязательные проверки

5.1. Открыть статью и сохранить без правок — файл не меняется ни на байт. Проверяется на всех статьях сайта, а не на выборке, и именно тем путём, которым сохраняет сервер: шапка собирается заново, а не приклеивается исходным куском. Проверка «разобрал и склеил обратно» пропускает целый класс поломок. Команда проверки — `npm run editor:corpus` (корпусный прогон): она же прогоняет по статьям сайта местные правила подготовки — те, которым не нужны ни диск, ни дочерние процессы, — и печатает сводку. Проверка качества и полная сборка в неё не входят, поэтому зелёная сводка прогона не означает «подготовка прошла бы». Правила она зовёт те же, что и сервер, своих не заводит; собственные меры у неё только про сам прогон — полнота обхода (пустой корень сайта, ноль проверенных статей при найденных файлах и пустой снимок статьи делают прогон красным, иначе «ноль изменившихся» означало бы «ничего не смотрел») и признак «шапки в файле нет», который считается по первым знакам файла, а не по успеху разбора: иначе файл с нераспознанной шапкой сошёл бы за файл без шапки. Расхождение собранного текста с файлом красное всегда, кроме двух случаев, объяснимых самим файлом: в нём разные переводы строк либо нет шапки. Правила прогона закреплены тестами наравне с правилами программы (SPEC 5.2).
5.2. У каждого правила есть свой тест, и **имя теста повторяет формулировку правила**. Отдельного списка правил не ведётся: список — это вывод `npm run editor:test`, он не может разойтись с кодом. Рукописная таблица «правило → файл» запрещена: она устаревает в тот же день.

5.2.1. Тест проверяет результат функции или запроса, а не наличие строки в коде. Структурные тесты (поиск подстроки в исходнике: «настройка читается кодом», «файл не длиннее 300 строк», «реестр не пишет файлы») допустимы только как предохранители от регресса, а не как доказательство поведения; где поведение можно проверить результатом — проверяем результатом.
5.3. Быстрые проверки при каждом сохранении укладываются в доли секунды: метаданные валидны, `image` без пробелов и не пустой, пути картинок существуют, MDX разбирается, внутренние ссылки целы. **При сохранении сегодня сделана только защитная правка шапки (З19 в `TASKS.md` — про сохранение).** Картинки, обложка, разбор MDX, JSX-блоки и внутренние ссылки проверяются в ходе публикации — быстрыми проверками против будущего сайта (5.4, `fastChecks.mjs`, решение владельца 2026-09-18).
5.4. Порядок публикации: обязательные проверки (шапка, содержимое, адреса, разбор MDX изменённых файлов, внутренние ссылки против будущего сайта — основа плюс план) → показ состава и единственное подтверждение → запись коммита от закреплённой основы → отправка. Полной сборки сайта на компьютере нет (решение владельца 2026-09-18): сайт собирает GitHub Actions, при неудаче живой сайт остаётся прежним, а программа следит за выкладкой и называет упавший шаг. Быстрые проверки — не доказательство сборки: невыполненные этапы называются в отчёте.

5.4.1. Как это устроено (решение владельца 2026-09-18, п.2–5). Единственный вопрос задаётся окном «Опубликовать» ДО хода: нынешнее состояние версии на сайте (по опубликованной основе), выбор доступности («Доступно всем» по умолчанию · «По ссылке» · «Недоступно»), при «Недоступно» у опубликованной версии — сколько статей получат правку ссылок, свёрнутые замечания проверки. Дальше ход идёт сам. Доступность назначается только публикацией: в свойствах статьи её нет. «Недоступно» у версии, чья страница сейчас на сайте, убирает ссылки на неё той же записью, а после отправки — и на компьютере, в файлах и подтверждённых черновиках соседей. Быстрые проверки (`fastChecks.mjs`, `core/fastRules.mjs`) выбраны по причинам упавших сборок на GitHub (`JOURNAL.md`, 2026-09-18): картинка, которой нет, `{#id}` в заголовке (разбор MDX тем разборщиком, которым собирает сайт), ссылка на страницу, которой нет (`onBrokenLinks: 'throw'`), неизвестный JSX-блок (сверка с `src/theme/MDXComponents.js`), `draft`+`unlisted` разом, обложка на пустое место. Ложный блокер хуже пропуска: где правило судить не берётся, оно предупреждает. Вместо сверки с деревом сборки запись сверяет дерево с планом: git называет (`diff-tree`), чем дерево отличается от основы, и это обязано совпасть с путями плана. Отказ открывает окно причины сразу: одна строка словами человека (что случилось и что сделать), «На сайт ничего не ушло» — когда это правда, «Показать ссылку» / «Показать место»; после успеха человеку говорится только то, что требует его действия. Выкладку на GitHub показывает значок «Сайт» (открытый API, ETag, лимит); учебный сайт не на GitHub значка не имеет (решение владельца 2026-09-19). Непроверенное быстрыми проверками после успешной публикации человеку не показывается; на сайте не на GitHub его не показывает никто — осознанный выбор владельца 2026-09-19: человеку сообщается только то, на что он может ответить действием. Записи окна в одном ходе (доступность, дата блога, обложка) идут подряд, и каждая — от отпечатка файла, который сервер вернул после предыдущей (`useSaving.базаЗаписи`): ход держит обработчики мгновения нажатия, и без этого вторая запись уходила с отпечатком до первой, а сервер отвечал «файл изменён снаружи» (проба владельца 2026-09-21). Подставляется только отпечаток, пройденный собственной удачной записью того же захода; внешнюю правку между записями сервер видит и сводит, как прежде. Начатая публикация доходит до конца, куда бы человек ни ушёл: уход из статьи отменяет её только до того, как окно записало своё (сохранение, доступность, дата, обложка); отказ вне статьи называется полосой на любом экране с кнопкой «Открыть статью». Ссылки в полях шапки (например, `related:`) ни снятие, ни уборка, ни проверки не сканируют: таких полей в корпусе сейчас нет (замечание контролёра этапа 1).

5.4.2. Публикуются ОТМЕЧЕННЫЕ версии, а не одна открытая (этап 3, решение владельца 2026-09-18, п.2). В окне у каждого языка сайта — его состояние на сайте; галочка только у версии, чей файл есть; по умолчанию отмечен открытый язык, снять можно любой, без отмеченных кнопка заперта. Отмеченные уезжают с диска одним коммитом, неотмеченные — как прежде: на сайте — не трогаются, нет — заглушка. Доступность одна на все отмеченные. Открытому языку дату, доступность и обложку ставит окно своим сохранением, остальным отмеченным дату и доступность пишет сервер (`/api/publish/versions`, `mergeGate.записатьСверив`, снимки в историю); подтверждённый черновик, отличный от файла, или спор у такого языка — отказ «{ЯЗЫК}: есть несохранённая правка — откройте этот язык и сохраните»; языки пишутся все или никто (откат уже записанных), записанному готовность возвращается в черновик. Снимок подготовки, дата блога и те же байты сверяются у каждой отмеченной, отпечаток местных источников — по всем (запись очереди хранит `путиВерсий`, досылка сверяет их же). «Недоступно» убирает ссылки на каждую отмеченную живую версию одной записью. Цели уборки — и опубликованный (живой в основе) адрес, и местный: сменённый, но не выпущенный `slug` не оставляет ссылок на прежний адрес ни в коммите, ни на диске; ссылки из статей вне плана на страницу, уходящую с сайта, останавливают публикацию быстрой проверкой.

5.4.3. Лишние файлы папки статьи публикация убирает молча (решения владельца 2026-09-20 и 2026-09-21). Лишним считается файл в папке ОТМЕЧЕННОЙ версии, чьё ИМЯ не встречается ни в одном языке статьи. Ссылка ищется именем файла, а не разбором записи (`core/unusedFiles.mjs`): имя одинаково содержат и markdown-картинка, и `<img src>`, и обложка `image:`, и импорт, и карточка товара, и запись `@site/...` из соседней локали, — разбери правило каждый вид отдельно, первая же забытая запись означала бы удаление нужного файла. Счёт ссылок общий по ВСЕЙ статье И по всем статьям сайта: на картинку соседней папки ссылаются чужие страницы, и файл, названный только ими, трогать нельзя. Второй проход по корпусу идёт только при кандидатах (`adapters/unusedFacts.mjs`). Уборка — в папке каждой отмеченной локали своя. Никогда не лишние: служебные имена (`_state.json`, `_category_.json` — правилом `служебноеИмя`), файлы статей, обложка `cover.*`, файл без расширения. Не удалось узнать про язык (любой сбой stat, чтения или обхода, кроме `ENOENT` — «файла нет»), обойти статьи сайта или в папке лежит вторая статья — не убирается ничего. Найденное вычитается из состава ДО правила каркаса, поэтому с сайта эти пути уходят теми же записями `УДАЛЕНО`, какими уходит пропавшая с диска картинка; с диска они уходят в корзину редактора (перед отпечатком источников, иначе последний заслон перед отправкой счёл бы статью изменившейся) и возвращаются оттуда одним нажатием. Запись корзины несёт вид `лишниеФайлы`, и возврат говорит про файлы, а не про статью: статья всё это время стояла на месте. Чистка молчаливая (решение владельца 2026-09-21): ни окно «Опубликовать», ни ответ `/api/publish/state`, ни слова после хода лишних файлов не называют — картинку по имени не увидишь, и перечень только путал; согласием на уборку служит само согласие на публикацию. Найти и вернуть файл человек может в корзине: там запись «Лишние файлы статьи «…»». Если кроме лишнего файла публиковать нечего (его нет ни на сайте, ни в изменениях), уборку делает отдельная ручка `/api/publish/tidy` теми же заслонами и под тем же замком, а ход кончается прежними словами «публиковать нечего»; перечень лишних показ состава (`/api/release`) отдаёт только затем, чтобы ход знал, звать ли её. После досылки прежней записи «публиковать нечего» во втором проходе — успех, как и прежде, сколько бы лишнего он ни убрал. В «Доработать» уборки нет: её рабочая копия держит байты только используемых файлов, откатывать удаление нечем, а запись набора стирает файл насовсем; порядок «после переименования» при этом соблюдён сам собой — публикация идёт после доработки.

## 6. Обработка ошибок

Стандарт обязателен. Пишется вместе с методом, а не добавляется потом.

6.1. **Одна дверь к серверу.** Все запросы интерфейса идут через общий помощник `requestJson`. Прямой `fetch` в компонентах и действиях интерфейса запрещён.

6.2. **`requestJson` обязан:** проверить `response.ok`; безопасно прочитать JSON; при ошибке взять текст из `{error}` ответа; если сервер вернул не JSON — дать понятное сообщение; бросить нормальную ошибку с текстом для человека.

6.3. **Сервер всегда отвечает на API JSON-ом.** Формат ошибки единый: `{ "error": "человеческий текст" }`. HTML-страница ошибки, сырой stack trace и пустой ответ для API запрещены.

6.4. **Ожидаемые ошибки — с правильным кодом:** 400 — плохой запрос или битый JSON; 404 — нет статьи, картинки, файла; 409 — конфликт (файл изменился снаружи); 500 — внутренняя ошибка. Предел размера тела — тоже плохой запрос (400).

6.5. **Внутренняя ошибка видна, но без простыни.** Сервер пишет её в `console.error`, пользователю отдаёт короткий понятный текст без стека.

6.6. **Интерфейс не меняет состояние, пока сервер не подтвердил успех.** `save()` не показывает «Сохранено» и не сбрасывает признак несохранённого при ошибке; `pasteImage()` не вставляет `![](undefined)`; `replaceImage()` не перезагружает страницу, если файл не заменён. Видимость отдельного действия не имеет вовсе: она обычное поле шапки, и при отказе сохранения остаётся несохранённой правкой в окне, как заголовок или описание.

6.7. **Ошибка показывается спокойно и заметно:** без `alert` для обычных ошибок; текстом рядом с действием или в общей строке; не перекрывая статью; человек понимает, что именно не вышло; набранный текст остаётся на месте.

6.8. **Белый экран — последняя защита.** React Guard нужен, но обычные ошибки сохранения, загрузки, видимости и картинок ловятся до падения всего интерфейса, а не им.

6.9. **`readBody` безопасен:** битый JSON не роняет сервер; слишком большое тело отклоняется; ошибка чтения тела возвращает JSON 400.

6.10. **Тексты ошибок — в `settings.json`.** Всё, что видит человек и может меняться, живёт в настройках; в коде — только технические коды и внутренние имена.

6.11. **Тесты проверяют поведение, а не строки в коде.** Обязательный минимум: битый JSON → 400 JSON-ошибка; `save` при 500 не сбрасывает `dirty` и не показывает «Сохранено»; сохранение при 500 не меняет показанную видимость; `pasteImage` при ошибке не вставляет markdown; `replaceImage` при ошибке не перезагружает страницу; API отдаёт JSON-ошибку на ожидаемые сбои.

6.12. Полный «Отчёт об ошибке» с переходом к месту в статье — это В1-18. Раздел 6 — обязательный минимум, который есть уже сейчас, до автосохранения.

## 7. Запуск

7.1. Команда `npm run editor:dev`, адрес обычного окна — `http://localhost:4780`. Порт задан в коде (`src/core/runtimeIdentity.mjs`) и настройкой не является: см. 7.1.6.

7.1.1. **Постоянная папка материалов владельца — `C:/My_code/bimcore-blog`.** Она задана в коде (`src/core/materialRoot.mjs`), а не в настройках, и смена версии кода её не меняет: обычное окно читает и пишет статьи, картинки и переводы только там, из какой бы копии ветки ни был запущен код.

7.1.2. **Запуск называет себя сам.** В первых строках сервер печатает род экземпляра, версию запущенного кода, фактическую папку материалов и адрес. Корень проверяется по этим строкам и по реализации, а не по договорённости.

7.1.3. **Иной корень — только испытательный экземпляр.** Он включается переменной среды `EDITOR_TRIAL_ROOT` на один запуск и при старте назван испытательным. Выдавать его за обычное окно нельзя: Git, запись и публикация в нём привязаны к чужому дереву.

7.1.4. **Корень не годится — программа не запускается.** Путь не абсолютен, папки нет или в ней нет ни одной папки контента из настройки «контент» — сервер отказывается стартовать и называет причину словами. Тихой подстановки соседней папки не бывает.

7.1.5. **Черновики и история лежат при материалах, а не при коде.** Общее хранилище — папка редактора внутри фактического корня материалов; путь задан в коде (`src/core/draftHome.mjs`). Обычные экземпляры из разных рабочих копий кода с одним корнем материалов видят одно состояние; испытательный корень получает своё и состояния владельца не читает. Работа, оставшаяся в хранилище запущенной копии кода, переносится в общее ДО открытия сервера на запись; старое хранилище только читается, предел числа снимков при переносе не применяется, повтор переноса ничего не добавляет. Черновик опознаётся по статье внутри записи, а не по имени файла: обе схемы имён одного черновика сводятся к одной статье до всякого решения. Одинаковые копии сводятся только по байтам; разные черновики одной статьи не выбираются ни по времени, ни по пути — каждый сохраняется, а запись черновика этой статьи отклоняется понятным текстом до разбора. Беда чтения старого хранилища не считается отсутствием работы: отсутствующая папка — «переносить нечего», любая другая беда останавливает запуск до открытия сервера и называет путь и причину. Хранилище чужой рабочей копии забирается разовой командой `npm run editor:adopt -- <источник> <корень материалов>` с явно названными полными путями: она печатает оба пути до записи, только читает источник, отказывает вместо нулевого отчёта и не заводит ни настройки, ни режима — обычный запуск после неё по-прежнему читает только общее хранилище у материалов.

7.1.6. **`4780` принадлежит обычному принятому редактору, и опознание он выдаёт сам.** Принятый экземпляр доказывается четырьмя фактами о мире сразу: материалы владельца, папка принятой рабочей копии (`src/core/runtimeIdentity.mjs`), её ветка `editor` и чистое дерево кода. Меньшего не хватает: имя ветки берётся в любую копию, а несохранённая правка меняет поведение, не меняя ни ветки, ни коммита. Версия или чистота неизвестны — экземпляр не принят. Только принятый получает `4780`; любому другому запуску порт называют явно переменной `EDITOR_PORT` на один раз, и `4780` ему не отдаётся ни при какой заявке. Порт пришпилен в коде по тому же доводу, что и корень материалов (7.1.1). **Побочных портов у экземпляра нет:** горячая перезагрузка живёт на том же порту, иначе два экземпляра, разошедшиеся по главным номерам, сталкивались бы на общем побочном. Работающий сервер отвечает на `GET /api/identity` своим опознанием — род, ветка, коммит и чистота запущенного КОДА, папка кода, фактическая папка материалов, порт, собственный номер процесса и адрес. Номер процесса нужен панели экземпляров (7.1.7): система знает, кто держит слушающий порт, и совпадение этого номера с ответом сервера связывает живое опознание с конкретным процессом. Опознание одно на программу: те же факты печатаются первыми строками запуска. Ручка только читает. **Ярлык владельца сверяет ответ с git, а не верит признаку `accepted`:** папка кода и коммит должны совпасть с тем, что git говорит о принятой рабочей копии, иначе `4780` не открывается, а чужой сервер не подменяется и не завершается.

7.1.7. **Экземплярами управляет панель, а не чёрные окна.** Панель — отдельная программа (`panel.mjs`) на своём постоянном порту, пришпиленном в коде по доводу 7.1.6; портом экземпляра он не бывает. Она обязана работать, когда не поднят ни один экземпляр, поэтому страницей внутри редактора быть не может. Наблюдается ровно один порт — порт рабочего окна, заданный кодом; перебора портов нет, и настройкой этот список не расширяется. Панель — вход владельца, и строка в ней ровно одна: та, которой он работает. Испытательные экземпляры поднимаются своим способом и в панель не попадают. Само распознавание испытательного вида остаётся и проверяется: ответить с чужим кодом или чужими материалами может и тот, кто занял `4780`, и такую строку владелец обязан увидеть названной, а не принять за свой редактор. Состояние строки берётся ТОЛЬКО из живого ответа `/api/identity`; память панели даёт остановленной строке последний известный состав и работающим сервером никого не объявляет. Ответ, который опознанием не является, — препятствие: такой порт не открывается и не освобождается, а процесс на нём не завершается никогда. Остановка разрешена только после живого опознания и требует, чтобы порт держал ТОТ ЖЕ процесс, который ответил. Сервер называет свой номер сам, и он сверяется с владельцем слушающего порта, которого называет система; несовпадение — отказ даже при совпадающем пути, потому что между опросом и остановкой порт мог занять другой процесс той же рабочей копии, и по одному пути завершился бы чужой новый. Опознание без номера бывает у кода старше панели; тогда спрашивается сама система: пока связь, по которой пришло опознание, ещё открыта, она называет процесс, ОБСЛУЖИВШИЙ этот запрос, и он обязан совпасть с владельцем слушающего порта так же. Этот довод прямее прочих: в нём не участвует ничей рассказ о себе. Не назвала и система — остаётся последний признак, полный путь до `server.mjs` в командной строке владельца порта; косвенные признаки бывают недоступны сразу оба, и запуск `node .\server.mjs` кодом старше панели не даёт ни одного из них. Обычное управление идёт без окон консоли.

7.2. Сервер запускается напрямую, без сборки. Интерфейс собирается на лету.
7.3. Программа работает без интернета. Сеть нужна только для проверки удалённого репозитория, публикации и чтения состояния развёртывания.
