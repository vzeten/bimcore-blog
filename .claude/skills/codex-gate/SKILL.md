Проверку запускает Claude. Владелец не переносит технические запросы и ответы между помощниками.
Codex читает фактический локальный репозиторий в `C:\My_code\bimcore-blog` и не меняет файлы.

## Два уровня Codex

1. **Проверяющий операции** — одна постоянная сессия на всю операцию. Она помнит исходный замысел,
   принятые границы и прежние замечания. Консультации и промежуточные проверки продолжают её по ID.
2. **Независимый итоговый проверяющий** — один намеренно свежий read-only запуск только для опасного
   законченного результата. Он не заменяет проверяющего операции и не продолжает его историю.

Новая сессия на каждую мелкую правку запрещена: она снова тратит время на контекст и может повторно
оспаривать уже разобранное. `--last` запрещён: он способен выбрать чужую сессию.

## Файлы координации

Оба файла локальные и игнорируются Git:

- `editor/.coordination/reviewer.json` — машинное состояние проверяющего операции;
- `editor/.coordination/handoff.md` — один короткий обмен Claude, верхнеуровневого Codex и владельца.

Claude и Codex перед каждым обменом сверяют в обоих файлах:

- `operation_id`;
- `root` — строго `C:\My_code\bimcore-blog`;
- фактический `HEAD` и состояние рабочего дерева;
- растущий `revision` в `handoff.md`.

Расхождение root или операции останавливает работу. Файл `handoff.md` не растёт историей: следующий
обмен заменяет содержимое разделов. Предел — 120 строк.

## Состояния обмена

`handoff.md` содержит ровно четыре части:

1. заголовок состояния: `operation_id`, `revision`, `status`, `root`, `head`, `writer`,
   `codex_response_revision`;
2. **Отчёт исполнителя владельцу** — точный текст, который затем показан в чате, не длиннее 20 строк;
3. **Технические доказательства** — HEAD, `git status`, проверяемые файлы, итоги обязательных команд,
   живая проба и риски; без полных журналов;
4. **Ответ верхнеуровневого Codex** — только вердикт, доказанные замечания и следующее разрешённое
   действие.

Рабочие статусы:

- `claude-working` — Claude работает, ответ Codex от прошлого обмена уже прочитан;
- `awaiting-codex` — отчёт и доказательства готовы, верхнеуровневый Codex должен проверить;
- `codex-answered` — ответ записан, Claude ещё не подтвердил чтение;
- `awaiting-owner-test` — техническая работа завершена и ждёт живой пробы владельца;
- `closed` — владелец принял результат.

Claude не заменяет отчёт, пока статус `codex-answered`: сначала читает ответ, меняет статус на
`claude-working`, затем начинает следующую законченную правку. Верхнеуровневый Codex записывает
ответ только при `awaiting-codex` и ставит `codex_response_revision` равным прочитанному `revision`.

## Одна постоянная сессия проверяющего

Путь к `codex.exe` всегда определяется динамически:

```powershell
$exe = (Get-ChildItem "$env:LOCALAPPDATA\OpenAI\Codex\bin" -Recurse -Filter codex.exe |
  Sort-Object LastWriteTime -Descending | Select-Object -First 1).FullName
```

### Первый вызов операции

1. Проверить `git rev-parse --show-toplevel`, `git rev-parse HEAD` и `git status --short`.
2. Создать `reviewer.json` со своим `operation_id`, root и HEAD; `session_id` пока `null`.
3. Запустить консультацию или первую проверку с JSON-событиями:

```powershell
& $exe exec -C "C:\My_code\bimcore-blog" --sandbox read-only `
  -m gpt-5.6-sol -c model_reasoning_effort=high --json -
```

4. Во входе передать замысел, критерии, границы, фактический HEAD/status и попросить первым делом
   подтвердить root. Ворота не читают Obsidian: всё нужное должно быть в репозитории и запросе.
5. Из события `{"type":"thread.started","thread_id":"..."}` взять точный `thread_id` и записать
   его в `reviewer.json` как `session_id`. Ответ без `thread.started` проверкой не считается.

### Каждый следующий вызов

Прочитать `session_id` из `reviewer.json` и продолжить только его:

```powershell
& $exe exec resume <ТОЧНЫЙ_SESSION_ID> `
  -m gpt-5.6-sol -c model_reasoning_effort=medium --json -
```

Возобновлённая сессия наследует исходные root и read-only sandbox. В запрос всё равно кладутся
нынешние HEAD/status, точный состав правки и просьба подтвердить root. Совпадение нового события
`thread.started.thread_id` с сохранённым ID проверяется машиной или глазами до принятия ответа.

Если `resume` не удался, один раз повторить тот же точный ID. Повтор не удался — записать статус
`resume-failed`, остановиться и сообщить владельцу. Запуск новой сессии, `--last` и молчаливая замена
проверяющего запрещены.

## Когда проверять

Число проверок задаёт риск, а не число изменений файла.

- **Простая локальная правка:** итоговая проверка законченного результата постоянной сессией.
- **Опасная операция:** консультация до кода определяет один или несколько смысловых рубежей.
  Основное правило проверяется до подключения к файлам человека, Git, публикации, локалям или UI.
- **Новая архитектурная развилка во время работы:** остановка и продолжение консультации в той же
  сессии. Решение владельца нужно только при изменении существенного пользовательского поведения.
- **Опасный законченный результат:** после постоянного проверяющего запускается свежая независимая
  read-only проверка полного результата. Её ID не подменяет `session_id` операции.

Проверка после каждого `Edit` запрещена. Проверяется законченная смысловая правка, которую можно
понять и доказать отдельно.

## Что получает проверяющий

**До кода:** цель владельца, понимание задачи, альтернативы, выбранное решение, границы, места чтения
и записи данных, риски, крайние случаи и будущие тесты. Проверяющий называет реальные пробелы и
вместе с Claude выбирает смысловые рубежи операции.

**После правки:** `operation_id`, root, HEAD/status, точный список файлов, локальный diff или полное
содержимое новых файлов, критерии приёмки, результаты обязательных команд и запись живой проверки.

Замечание блокирует только при доказанном нарушении критериев, поддерживаемого сценария,
существующих данных, безопасности или сохранности. Иная идея идёт хвостом в `PLAN.md` и текущую
операцию не расширяет.

## Контроль read-only и локального состояния

До и после вызова сравнить `git status`. Появившиеся от Codex изменения — нарушение: остановиться.
Копия GitHub не заменяет локальное дерево с незакоммиченными файлами. Если read-only sandbox не
стартует, сначала диагностировать системную песочницу; обход через другую копию репозитория не
засчитывается воротами.

## Как владелец участвует

Исполнитель сначала обновляет `handoff.md`, затем показывает владельцу **точно тот же** короткий
отчёт. В функциональных операциях редактора исполнителем остаётся Claude; поле `writer` не меняет
назначение ролей.
Владелец пишет верхнеуровневому Codex: `проверь Claude`. Codex читает общий файл и фактический
репозиторий, записывает ответ туда же и кратко отвечает владельцу. Затем владелец пишет Claude:
`прочитай ответ Codex и продолжай`.

Технические запросы, diff и ответы проверяющего владелец вручную не переносит.
