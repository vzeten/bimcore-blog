### Ветки и папки — статьи, редактор, код сайта

Основная папка `C:\My_code\bimcore-blog` всегда на `main`: здесь единственные рабочие материалы
владельца. Принятый код — ветка `editor` в `editor/.coordination/worktrees/accepted-editor`.
Версия кода не меняет папку материалов. `npm run repo:check` показывает состояние, ничего не
исправляет; несоответствие не разрешает удаление или переключение основной папки.

**Статья — создать, поправить, перевести, подготовить изображения:**
1. Claude или Codex выполняет запрос непосредственно в основной папке, без новой ветки или копии.
   Перед записью сверяет файл с автосохранением редактора; одну локаль одновременно пишет один
   исполнитель. При расхождении сначала сохраняет обе версии и разбирает различия, не затирает их.
2. Файлы сразу на своих местах: `blog/`, `docs/`, `i18n/`; применяются стандарт качества и навык
   статьи выше. Заполненные человеком поля и смысл сохраняются. Изменение доступности предпочтительно
   через окно; без окна — через существующее сохранение редактора с полной согласованной шапкой и
   актуальным текстом. Отсутствующее поле само по себе не запрещает сохранение; нельзя считать
   автосохранение записью файла или локальный HEAD опубликованным состоянием сайта.
3. Результат показывается ссылкой в рабочем редакторе (обычно 4780, фактический экземпляр проверяется).
   Публикация — кнопкой владельца или помощником по явному разрешению на точный пакет, включая
   необходимые медиа и удаления. Одно разрешение действует пока состав не изменился. Порядок —
   `it/web/learn/playbook-publish.md` в базе. Обычный push всей рабочей ветки недопустим; код и соседние
   статьи не включаются. Для публикации копию репозитория не создавать.
4. Цель, пути, результат, непроверенное и следующий шаг фиксируются в существующей карточке задачи
   базы по мере работы. Отдельную копию очереди или обязательный файл передачи статьи не создавать.
   Новый исполнитель сверяет карточку и фактические файлы, называет обнаруженное расхождение; владельцу не нужно завершать чат специальным словом.

**Код редактора:** единственный порядок — [Действующий процесс](editor/TASKS.md#действующий-процесс).
Одобренная операция разрешает одну ветку от `editor` и одну временную папку внутри
`editor/.coordination/worktrees/`; запись CURRENT_TASK фиксирует разрешение, но не создаёт его.
После приёмки — перенос в `editor`, проверенный запуск, затем безопасная уборка своей копии.
Неперенесённые tracked/untracked/ignored файлы и работающий экземпляр препятствуют удалению,
но не оправдывают потерю данных ради чистого отчёта. Выпуск `editor` в `main` — отдельное решение.
Страховки `backup/2026-09-12-main-folder` и `refs/backup/2026-09-12/*` удаляются только по слову владельца.

**Код сайта Docusaurus** (настройки, оформление, плагины сборки, скрипты) — третий объект в той же
папке; порядок отделён и от статей, и от редактора. Технический чеклист — `it/web/learn/runbook-site-ops.md`
в базе (инварианты архитектуры, сборка EN/RU/ES, один push, ожидание выкладки, проверка сайта).
1. Основная папка с материалами не переключается с `main`; код сайта не входит в публикацию статьи.
2. Разработка кода сайта — только по одобренной владельцем операции: одна ветка `feature/site-<суть>` или
   `fix/site-<суть>` от актуальной серверной `main` и одна временная папка внутри
   `editor/.coordination/worktrees/`; цель переноса — `main`, не `editor`. Незавершённые статьи и чужой
   код в выпуск не включаются.
3. Проверки свои: инварианты, сборка EN/RU/ES зелёная, проверка того, что правка меняет на сайте.
   Проверка по ущербу: обычную обратимую правку проверяет исполнитель сам; независимый контролёр
   зовётся при существенном риске (публикация, удаление, настройки сборки, общие компоненты). Ведущий
   принимает результат по отчёту и пробе, повторный аудит не проводит.
4. Выпуск — по серьёзности (пункт 3) до разрешения назвать независимого проверяющего другой системы или
   записать, что он не нужен; показать точный состав, получить разрешение владельца, один push, дождаться
   выкладки, проверить сайт запросами (для видимых изменений — и в браузере). Принятая схема сама по себе не
   разрешает commit, merge или push. Выпуск завершён, когда пройдены выкладка, проверка сайта, приёмка и
   сверка main: `npm run repo:check -- --release-site` выходит с кодом 0 (основная папка на `main`, её HEAD
   равен настоящей серверной `main` по ls-remote, не `origin/main`, нет незакоммиченного кода и процессных
   файлов; незаконченные статьи не мешают). Код 0 — только это одно условие, не доказательство выпуска. Иначе
   выпуск остаётся незавершённым с названным препятствием; приведение локальной `main` к серверной — отдельное
   разрешение владельца на точные шаги, без потери файлов и локальных коммитов, не во время записи статей.
   Уборка ветки и копии — после проверки отсутствия неперенесённой работы.
5. `npm run repo:check` знает эти ветки наравне с ветками редактора и показывает их как ветку операции.

### Редактор статей

Вход — [состояние процесса](editor/process/README.md) и `editor/CURRENT_TASK.md`.
[Действующий процесс](editor/TASKS.md#действующий-процесс) — единственный порядок отбора работы,
ролей, проверок по риску и завершения. Верхний Codex не дублирует технический аудит.
Исполнитель и замена при лимитах определяются разделом ролей TASKS; ведущим может быть Codex или Claude.

`BUSINESS.md` хранит утверждённый смысл продукта, `SPEC.md` — технические свойства,
`MAP.md` — указатели на код. Открывать только фрагменты по операции.
`PLAN.md`, `MVP.md`, `DECISIONS.md`, `JOURNAL.md` и `IDEAS.md` — справочная история,
не очередь; читать по точной необходимости, а не для восстановления всей биографии проекта.

Навыки служат входами в отдельные действия: `editor-change`, `codex-gate`,
`editor-live-check`, `model-council`. Новый набор правил вокруг них не создавать.
Запуск видимой Claude-сессии, статусы `run-status.json` и ожидание — раздел «Передача между чатами и сессиями» в `editor/TASKS.md`; отдельной программы ожидания нет.
После остановки нужен короткий отчёт по [REPORT.md](editor/REPORT.md).

**Секрет Obsidian.** Bearer token не выводить, не сохранять и не пересказывать.

### ⛔ Браузерный плагин (Claude in Chrome / Comet) — только крайнее средство

Управление браузером (`mcp__Claude_in_Chrome__*`, скриншоты, клики, навигация) **запрещено для рутинных задач**. Включать его ТОЛЬКО когда:
- задачу иначе никак не решить (нужна живая сессия пользователя, File System Access, измерение в реальном UI), ИЛИ
- альтернатива явно дороже по ресурсам/времени.

Сначала всегда пробовать дешёвые способы: чтение файлов, `curl`/`Invoke-WebRequest`, лог dev-сервера, поиск по коду/докам. Проверка «работает ли сайт / есть ли ошибка» = HTTP-запрос + лог сервера, НЕ браузер. Если кажется, что нужен браузер — сперва спросить себя, нет ли способа без него, и при сомнении спросить пользователя.

**Запрет не касается редактора статей.** Живая проверка программы во встроенном окне на `localhost:4780` обязательна — порядок в навыке `editor-live-check`. Запрет выше относится к внешнему браузеру с вашей живой сессией (Claude in Chrome, Comet) для рутинных задач и его не отменяет.
